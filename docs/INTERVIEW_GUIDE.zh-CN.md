# VocalStream：从读懂项目到面试讲解

[项目首页](../README.zh-CN.md) · [简历版本](CV.md) · [结果与边界](RESULTS.zh-CN.md) · [窗口优化](WINDOW_INFERENCE.md)

这个项目围绕一个问题展开：**已有的人声分离模型，在只需要人声、并且希望尽快输出时，能减少哪些计算；代价和剩余瓶颈是什么？** 学习时沿着输入、模型、评估、优化、结论这条线走。每一阶段以能完成一个小任务为准，不要求先读懂所有神经网络源码。

## 先分清几样东西

| 名称 | 在项目中的作用 |
| --- | --- |
| Python | 编写数据处理、模型调用、实验和报告的编程语言。 |
| PyTorch | 执行张量计算和神经网络的框架；它本身不是分离模型。 |
| Open-Unmix | 基线模型及参考实现，帮助建立比较起点。 |
| BS-RoFormer | 主要研究的分离网络；本项目使用社区发布的预训练权重。 |
| MUSDB18-HQ | 包含混合音乐及对齐分轨的数据；其中原始 vocals 是客观评估的参考。 |
| SI-SDR / SI-SDRi | 衡量估计人声与参考人声的关系，以及相对未处理输入的改善。 |
| RTF | 处理耗时除以音频时长；必须说清楚测量的工作量和计时范围。 |

BS-RoFormer 是被评估的模型。我们用 MUSDB 的参考人声与指标评估它，并不把它自己的输出当作所有模型正确性的标准。

## 六次学习安排

每次约45–90分钟，可拆成更短的几次。先做“完成标志”，再进入下一次。

| 次数 | 本次要理解什么 | 阅读入口 | 完成标志 |
| --- | --- | --- | --- |
| 1 | 采样率、声道、混合与分轨、推理输入输出 | [data.py](../vocalstream/data.py)、[evaluate_project.py](../evaluate_project.py) | 画出 mixture → separator → estimated vocals，并标出 reference vocals 只进入评分；算出44.1 kHz双声道30秒的数组形状。 |
| 2 | STFT、频带、时间/频率建模、掩码和波形重建 | [模型适配器](../vocalstream/bsroformer.py)、[供应者 forward](../vocalstream/vendor/zfturbo_bsroformer/bs_roformer.py) | 用自己的话讲出波形 → 时频表示 → 频带特征/Transformer → 复数掩码 → ISTFT；指出共享主干和四个输出分支。 |
| 3 | SI-SDR、串音实验、RTF与延迟 | [metrics.py](../vocalstream/metrics.py)、[conditions.py](../vocalstream/conditions.py)、[方法](METHODOLOGY.md) | 手算一个RTF；解释为什么单靠SI-SDR不能全面衡量音量保真，为什么 −20 dB伴奏增益不是固定SNR。 |

| 5 | 过去缓存、输出块、未来信息、整窗重算 | [streaming.py](../vocalstream/streaming.py)、[window_inference.py](../vocalstream/window_inference.py)、[窗口研究](WINDOW_INFERENCE.md) | 画出一个2秒窗口，解释80/40 ms设置的输入等待、计算预算，以及为什么91 ms仍不够。 |

第一次的数组答案是 `(1_323_000, 2)`，表示采样帧数与两个声道。不是把两个声道拼成一条长度翻倍的时间序列。

## 项目的数据流

```text
MUSDB mixture ──> 固定采样区间 ──> 预训练分离器 ──> estimated vocals
                                                           │
MUSDB vocals ───> 相同采样区间 ───────────────────────────────> 质量评分

分离调用开始/结束 ──> 同步GPU计时 ──> RTF、逐块预算与虚拟排队
```

音频和参考必须采样率、声道数、长度及时间位置一致。参考人声只参与评分，不能进入推理输入或用来偷偷选择每块最好的结果。没有对齐分轨的普通歌曲可以试听，但不能直接计算这种有参考的客观分数。

## 三个必须能讲清楚的实验

**实验一：只计算需要的人声分支。** 固定模型先完整、严格加载四分轨权重，然后在内存模型中保留原来的人声输出分支。四个分支位于共享主干之后，所以省去其他三个分支仍可保留同一个人声计算路径。在当前工作负载中，FP32、AMP各自比较时，14/14个保存波形逐采样一致。活动参数从约1.317亿减到5780万，但单独加速只有约2%–4%；共享主干依然要计算，参数量不能代替计时。

**实验二：结合混合精度。** AMP允许适合的运算使用较低精度，而模型不需要重新训练。四分支FP32与仅人声AMP的三次计时RTF中位数分别为0.386387与0.164287，因此吞吐比约为2.35。大部分组合加速来自AMP。AMP和FP32的输出并不逐采样相同，项目另外记录了它们的质量和波形差异。这里没有量化或压缩原始checkpoint文件。

**实验三：去掉窗口内部的第二次推理。** 外层流式代码每次收到足够的输入，重算2秒上下文，再裁出20或80毫秒输出。原离线适配器又在这个上下文内部做两次推理和重叠平均；第二次使用后1秒输入加1秒补零。新路径直接对整窗推理一次。这会改变最终预测，需要重新比较质量。在三首4秒片段的25项研究中，单块计算中位数约183→91 ms，四种设置的逐曲质量变化中位数均为正，但两处个别歌曲略有下降。每首歌每种设置只有一次计时，不能称为稳定的多次重复加速基准。

## 用一个窗口算清楚“快”与“低延迟”

令缓存过去为 `P`、输出块为 `E`、块尾之后额外观察的未来为 `L`：

```text
输入窗口：[s-P,           s,       s+E,         s+E+L)
             过去 P        输出 E      额外未来 L
```

2秒上下文、80毫秒输出、40毫秒未来信息，对应 `P = 1.88 s`。对第一个输出采样边界来说，正常情况下需等 `E+L = 120 ms` 的输入，再加计算和可能的排队。过去1.88秒已经收到，不是需要重新等待的未来。

输出每80毫秒产生一块，如果计算平均需要约91毫秒，系统就会逐渐落后。本次实测该设置的工作量RTF为1.143。把窗口计算改快约两倍是有价值的，但它仍没有按80毫秒周期及时交付。`L=0`也不意味着逐采样零延迟：同一输出块后面的样本仍可用于预测前面的样本。

本项目记录了根据输入到达时间和实测计算时间推演的虚拟队列，尚未用声卡实测麦克风到扬声器的总延迟。

## 面试60秒介绍

下面是学习完成后的练习稿。按自己实际参与和理解程度调整措辞。

> 我围绕低延迟人声分离做了一个个人研究项目，使用Codex辅助实现和组织实验。我先复现Open-Unmix和教授推荐的BS-RoFormer，用MUSDB18-HQ的对齐人声分轨建立客观评测。接着研究只输出人声时能省掉哪些计算：保留原人声分支后，活动参数减少56.1%，结合混合精度，在固定GPU上测得约2.35倍离线吞吐。之后我把输入限制为滚动窗口，发现很短的输出周期会产生大量重算，便移除了窗口内部的一次重复推理。在三首短片段的对照中，每块计算约从183毫秒降到91毫秒。它仍超过20或80毫秒的预算，这让我明确区分了吞吐、输入等待和实际设备延迟。下一步希望扩大验证，并研究更短上下文或适合流式处理的网络。

## 常见追问与回答要点

**你做了哪些工作，哪些来自已有模型或工具？** 预训练网络、权重和供应者实现来自已有开源工作；项目围绕人声任务组织了适配、对照实验、报告和推理路径优化，使用了Codex辅助。说明自己实际作出的需求选择、参与过的结果分析和已经掌握的代码。如果某段代码尚不能解释，应如实说明正在补齐；不要说所有代码都由自己独立手写。

**你的创新在哪里？** 可以展示任务适配、运行成本分析、实验设计和重算路径的改进。没有提出新的分离架构，也没有通过从零训练得到新的分离模型。对于研究实习，能解释假设、对照、结果和下一步验证，是这个项目的核心价值。

**为什么不用BS-RoFormer的结果作为标准答案？** 它本身也会犯错。MUSDB提供与混合音乐对齐的原始人声分轨，才能直接检查估计误差。BS-RoFormer在项目中是较强的模型参照，仍需要接受评估。

**SI-SDR衡量什么？** 把估计信号投影到参考信号上，比较参考方向的成分与剩余误差的能量比。简式为 `alpha = <y,s>/<s,s>`，`10 log10(||alpha*s||² / ||y-alpha*s||²)`。实现先按声道减均值，再展开立体声并拟合一个共享比例。它允许整体增益变化，所以还记录不拟合增益的波形误差。这个分数不能直接等同于论文里的所有SDR协议。

**SI-SDRi与SI-SDR有什么区别？** 前者等于输出SI-SDR减去同一输入的SI-SDR，回答处理比保持原输入改善多少。原本很干净的输入如果被损伤，SI-SDRi可以为负。

**参数减少56.1%，为什么单独只快2%–4%？** 被移除的分支参数较多，但总耗时仍受共享网络、运算形状、内存访问和数据传输影响。2.35倍来自分支选择与AMP的组合；需要分别做消融才能分清贡献。

**两次加速能相乘吗？** 不能。2.35倍来自11秒上下文的离线分支/精度比较；约2倍来自2秒上下文的流式窗口政策比较。基线、工作量和计时范围不同，不能乘成一次端到端加速。

**为什么质量也会变化？** 新窗口路径移除了一个经过补零和加权的预测，并不是只删除不会影响输出的代码。固定输入时间表、权重和精度后，必须重新测量质量。四组中位数改善不保证每首歌曲都改善，更不等于完成了主观听音评价。

**0.164的RTF是不是就可以实时监听？** 这只是特定离线工作量下处理时间小于音频时长。模型可能仍需收集长窗口、观察未来音频并等待输出拼接。实时监听还要满足逐块截止时间并测量设备输入输出链路。

**能否直接给Transformer加KV缓存？** 这个模型含双向时间注意力，新窗口的上下文会改变过去位置的表示，不能直接照搬自回归模型的缓存并假设数值等价。必须明确复用的状态、输入依赖和误差，或采用为因果/流式处理设计并训练的网络。

**为什么只用14首/3首？够证明什么？** 当前工作是开发阶段的固定片段研究，适合排查工程假设。它不能证明整曲或真实现场泛化，而且外部checkpoint的完整训练曲目名单不明。重复计时也不会增加独立歌曲数量。

**如何对应岗位中的串音和声学反馈？** 目前完成的是对齐伴奏按增益混入人声的受控串音代理，以及原人声输入的保留实验。没有模拟真实麦克风空间传递，也没有建立扬声器—房间—麦克风的声学反馈闭环。后者需要另设数据和系统实验。

**你会先做什么后续工作？** 先对有希望的设置重复计时，并扩大到更长和更多开发片段、检查输出边界与试听；再比较较短上下文能否满足计算预算。因果网络、状态复用、真实麦克风和设备延迟属于随后更大的研究范围。

## 面试前独立完成的小练习

1. 写出20毫秒、44.1 kHz对应多少采样点；写出2秒上下文、20毫秒输出、40毫秒前瞻时的过去长度和首边界输入等待。
2. 给一段4秒音频，如果分离调用耗时0.8秒，算RTF，并说出还缺什么信息才能判断监听延迟。
3. 解释“前后两组中位数相减”和“每首歌先相减再取中位数”为什么可能不同。
4. 打开人声分支代码，指出为什么在完整严格加载权重之后才移除另外三个分支；指出人声索引来自哪一个分轨顺序。
5. 打开一份 `single` 流式报告，找到输入依赖边界、`model_forward_passes`、处理时间、是否超出预算以及EOF标记。
6. 对照两份输出，指出哪些质量差异是已经测到的，哪些听感、真实设备或泛化结论还没有证据。

前两题答案：20毫秒为882个采样点；过去长度1.94秒，首边界输入等待60毫秒；RTF为0.2，但还需知道输入窗口/前瞻、拼接、逐块截止时间以及设备缓冲等。学习完成的标准是能从代码和报告说明理由，而不只是记住这些答案。
